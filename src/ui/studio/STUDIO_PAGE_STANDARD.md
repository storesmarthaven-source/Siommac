# SIOMAC Design System Studio component standard

This document is the required implementation contract for every component page,
family page, variant selector, inspector and catalogue thumbnail. The canonical
component implementation and typed registry remain the single source of truth.
The Action Button page is the visual baseline; exceptions require an explicit
typed reason, not a bespoke page.

## 1. Architecture status and target

### What is shared today

- `ComponentDef` is the authoritative component definition.
- Generic pages are generated by `Workbench`.
- `PropControl` schemas are rendered by the shared `Control` property engine.
- `StyleControl` schemas are rendered by `GeneratedStyleControls` and persisted
  through the shared `GalleryDraft` theme/recipe draft.
- Preview values are isolated by component + preview axis + selected value.
- Generic variant cards are generated from `previewAxis` and `previewSamples`.
- Every inspector uses the shared `StudioInspector` shell; generic and compound
  component properties use the shared `Control` engine.
- Conditional fields are declared with typed `visibleWhen` rules in the
  component schema; the property engine contains no component-ID visibility
  branches.
- Compact icons, comparison-only props and structural diagrams are selected by
  typed `VariantSample` metadata; the variant engine contains no component-ID
  rendering branches.

### Known gaps that must be removed

- Action Button still uses the specialized `RecipeStyleEditor`.
- Compound buttons still use `CompoundButtonEditor`.
- Action Button keeps a scoped recipe composition for variant + state editing,
  but it uses the same inspector shell, typed registry and `GalleryDraft` style
  controls. It must not grow a separate persistence contract.

The implemented contract is one schema-driven property engine, one draft/style
engine, one variant engine and one typed thumbnail contract. Specialized
renderers are allowed only for the specimen, diagram or governed scope picker;
they must not create a second settings or persistence system.

## 2. Required page anatomy

Every standalone component page uses this order:

1. Global Studio draft/history/review/publish bar.
2. Breadcrumb and component navigation.
3. Page heading and one-sentence purpose.
4. Live canonical preview on the white dotted canvas.
5. Variant or layout cards attached beneath the live preview.
6. Common application use, using real SIOMAC examples.
7. Sticky properties panel on the right.

Do not add Usage, Accessibility or Code tabs to the primary editing flow. Those
contracts belong in registry metadata, documentation and tests. The editing page
must stay focused on selecting a component, previewing it and changing governed
settings.

### Desktop dimensions

- Workbench maximum content width: `1180px`, centered.
- Main/editor columns: `minmax(0, 1fr) 330px`, `18px` gap.
- At widths below `1024px`, inspector may reduce to `280px`.
- At widths below `520px`, preview and inspector stack.
- Live preview canvas minimum height: `300px`; narrow screens: `250px`.
- Preview canvas padding: `36px`; narrow screens: `26px`.
- Page heading: `30px`; description: `14px`, maximum `76ch`.
- Section/card radius: `12px`; inspector radius: `16px`.

Do not shrink component text or apply arbitrary scale transforms to make the
workbench fit. Change the comparison representation, not the canonical component.

## 3. Family pages

A family page is used only when several canonical components share a clear job
but own different behaviour, for example Action, Dropdown and Split Button.

- Family choices are component tabs, not variants.
- Each choice shows a real compact specimen, component name and one short role.
- Selecting a member replaces the complete preview and inspector subject.
- Members do not share preview props unless the registry explicitly declares a
  shared foundation.
- Do not create a family for unrelated components merely to reduce navigation.

## 4. Property engine

### One engine rule

Every visible property must be declared in the selected component's typed
`props` schema and rendered by the shared property engine. A component page must
not hand-build its own switches, fields or dropdowns.

The only permitted specialized UI is a reusable control type—such as icon
picker, color picker or diagram selector—which must then be available to every
component schema.

### Control anatomy

The shared property engine owns the visual and interaction contract for every
inspector control. Component definitions provide typed data; they must not
recreate these controls locally.

- Select controls use `StudioSelect`. Its trailing chevron is a separate,
  full-height segment with a separator and the same hover, focus and disabled
  treatment everywhere. Do not use a browser-native arrow, a text glyph or a
  component-specific chevron.
- Color properties use the `color` `PropControl` type and
  `StudioColorControl`; they do not use a plain text field. The color trigger
  uses the same split-chevron affordance as `StudioSelect`.
- Concise help is declared with `PropControl.help` and rendered with the
  canonical `InfoTip`. The trigger is a circled question-mark immediately after
  the property label; it must never occupy the value or chevron area of a field.
  Help opens as an accessible tooltip on hover and keyboard focus.
- Do not render expandable “About this setting” sections, permanent help copy,
  or raw implementation values in the inspector.

The canonical implementation points are `Workbench.Control`, `StudioSelect`,
`StudioColorControl` and `InfoTip`. A new reusable control type must be added to
the typed schema and this engine before a component can use it.

### Property groups and order

1. **Preview options** — Reset and the single State selector.
2. **Content** — icons, icon placement, optional supporting elements.
3. **Appearance** — variant-owned presentation choices that are not recipe CSS.
4. **Elements** — optional canonical subparts.
5. **Options** — remaining behaviour supported by the component contract.
6. **Component style** — the only collapsed section; governed recipe controls.

Do not expose Small/Medium/Large in the right panel. Size remains supported by
the component API but the Studio shows the canonical default. Do not expose
editable preview labels. Preview wording is registry-owned demonstration data.

### Required property behaviour

- Every visible control updates the live preview immediately.
- Every preview-axis value owns separate preview values and state.
- Reset affects only the selected component + variant, except an explicitly
  shared composition such as App Top Bar.
- If State already contains Disabled, Loading or Error, do not duplicate it as
  a checkbox.
- Conditional visibility must be declared as typed schema conditions; adding new
  component-ID branches to Workbench is prohibited.
- Labels are human language. Never expose CSS variable names, raw token paths or
  values such as `rgba(...)` as the control label.
- Preview props never enter a published payload.

## 5. Governed component style

Component style controls edit recipe variables through the existing theme draft;
they do not create a parallel styling store.

Every component should expose only applicable controls from these groups:

- Typography: weight, size and line-height where the component owns them.
- Geometry: height, padding, gap and radius.
- Borders: width, style and color.
- Colors: surface, text, icon, accent and semantic status colors.
- Icons: size, color and circle treatment when the component owns an icon.
- States: hover, active, focus, disabled and loading visual values.

Controls must support theme-linked and component-override modes. Variant-specific
controls must declare their variant scope; state controls must declare their
state scope. Shared controls are allowed only when all variants genuinely inherit
the same foundation.

Locked and never editable:

- Component semantics and canonical variant enums.
- Keyboard behaviour, focus management and ARIA contracts.
- Arbitrary CSS or selectors.
- Behavioural contracts such as menu ownership and dialog focus trapping.

## 6. Variant card standard

Variant cards are selectors, not miniature live-preview pages.

### Card anatomy

- Up to six cards stay on one desktop row.
- All cards in a row have equal width and equal height.
- One centered specimen area sits above one compact label footer.
- Footer minimum height: `31px`, with a top border and centered `12px` label.
- Standard compact card minimum height: `98–108px`.
- Gap between cards: `8–10px`.
- Selection circle appears only on hover, keyboard focus and selection.
- Empty circle: transparent with a light neutral outline.
- Selected circle: very light neutral fill; never blue-grey.
- The selected card border remains thin and neutral.

The card must show the real canonical component whenever it remains readable.
Use the component's supported compact size or shorter preview content; never use
CSS scaling, compressed typography or clipped overflow.

### Choosing the comparison representation

- `compact`: buttons, badges, switches, short inputs and other specimens that
  remain legible in a standard card.
- `diagram`: dialogs, modal frames, application bars, tables, complex calendars,
  drawers and any specimen whose natural width exceeds its card.
- `wide`: reserved for one large layout choice that has no meaningful diagram;
  it is not a way to stack ordinary variants.
- More than six variants use a compact icon/tile selector with readable labels.

If a real specimen is too large, build a purpose-made code diagram like the Modal
Frame selector. The diagram must:

- Show only structure relevant to choosing the variant.
- Use theme variables rather than fixed brand artwork.
- Remain centered and readable without scaling a full application screen.
- Keep the full canonical component in the live preview above.
- Be registered through typed metadata, not a component-ID conditional.

### Variant wording

- Use realistic SIOMAC language.
- Titles are short nouns or treatments: Outline, Soft, Range, Sidebar left.
- Add at most one concise sentence when the distinction is behavioural.
- Do not use Option 1, generic pricing plans or implementation terminology.
- Action roles such as Next, Save and Delete remain usage examples, not variants.

## 7. Live preview

- White canvas with a very light neutral dot pattern (`20px` grid).
- The canonical specimen is centered and given enough room to demonstrate its
  normal dimensions and state.
- Company theme values are scoped to the preview only until publish.
- State forcing must use the component's supported preview contract.
- Preview content and properties are local and never published.
- Dense application compositions may offer a separate full-preview action, but
  it cannot replace the normal component preview.

## 8. Catalogue cards and thumbnails

### Shared card dimensions

- Catalogue grid card width: `320–386px`; one or two cards do not stretch wider.
- Thumbnail canvas: `156px` high.
- Canvas background: white with an `18px` very-light-neutral dot grid.
- Footer padding: `10px 13px 11px`.
- Component title: `14px`; metadata: `12px`.
- All component and family cards use the same frame, radius and footer anatomy.

### Thumbnail rules

- Build the thumbnail in code so it follows active theme tokens.
- Prefer the canonical component or a faithful code composition.
- Do not use screenshots or raster references as the implementation.
- Center the primary interaction and preserve its proportions.
- Crop the surrounding composition, never the component itself.
- Use fade/blur only when content intentionally continues below the crop.
- Never blur the primary control; never apply blur to every thumbnail.
- Simple components show one representative specimen.
- Dense components show a simplified composition or structural diagram.
- Family thumbnails show the family relationship, not an arbitrary member.
- Thumbnail scenes must be typed registry metadata so a new component does not
  require editing a central ID switch.

## 9. Registration contract

Every new component definition must provide:

1. Stable `id`, name, category, status and one-sentence purpose.
2. Canonical component path and barrel import.
3. Typed prop schema containing every visible preview control.
4. Governed style schema with linked token and explicit scope metadata.
5. Supported states and accessibility contract.
6. `previewAxis`, samples and deliberate `previewLayout` when variants exist.
7. Real SIOMAC application examples where they clarify correct use.
8. Typed thumbnail scene metadata.
9. Canonical renderer and accurate usage snippet.
10. Migration/adoption metadata where legacy consumers exist.

## 10. Completion gate

A component page is not complete until all items pass:

- Registry is the only source of component data.
- No bespoke property or persistence engine was introduced.
- Every control visibly works; no accept-and-drop settings exist.
- Preview values remain isolated per component and variant.
- Variant cards follow the shared card anatomy and stay one row when six or fewer.
- Oversized variants use a professional typed diagram.
- Live preview shows the real canonical component.
- Thumbnail matches the shared card size and is theme-aware code.
- Default, hover, focus, active, disabled and loading states work where applicable.
- Keyboard and ARIA contracts remain locked and verified.
- Draft changes remain preview-scoped until publish.
- Published recipe changes reach every canonical runtime consumer.
- Desktop and narrow layouts are visually verified.
- Focused unit/integration coverage exists, followed by the final full test gate.

## 11. Prohibited patterns

- Bespoke page or inspector for one component.
- New component-ID branches in the generic property engine.
- Duplicate prop/state controls.
- Variant values invented from action roles.
- Preview content entering persistence.
- Fixed screenshots used as ordinary component thumbnails.
- Scaling or shrinking real UI until it becomes unreadable.
- Raw CSS, token names or implementation values exposed to non-technical users.
- Publishing from an individual component section instead of the global draft.
